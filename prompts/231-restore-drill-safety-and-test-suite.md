# 231 — restore drill safety and automated test suite

## Scope and why this is next

Phase 12K remains open at committed `515b16a` on `main`: the operator launch sign-off and live infrastructure evidence are still outstanding. Prompt 230 hardened the secret rotation drill and added its dedicated test suite. The next dependency-safe repository step is the Stage 7 PostgreSQL restore drill, `scripts/ops/run-restore-drill.sh`, which has no dedicated test suite and can currently `DROP DATABASE IF EXISTS` on an operator-supplied drill name. This prompt makes that runner safe to invoke against a live PostgreSQL server, tests its command and evidence behavior without a real database, and wires the tests into the operations gate. It does **not** run a live restore or approve launch.

The current runner also accepts incomplete CLI options, accepts invalid RTO targets, emits `status: "success"` when `rto_compliant` is false, treats a failed `_prisma_migrations` query as zero, creates a timestamp-named dump that can collide with another run, and silently ignores cleanup failure. Its JSON is assembled with shell interpolation of paths. These are observable risks in the file at this commit, not evidence that any live drill has failed.

## Implementation plan

1. **Fail closed before side effects in `scripts/ops/run-restore-drill.sh`.** Keep `--help`/`-h` working without credentials or PostgreSQL. For `--source-db`, `--drill-db`, `--backup-dir`, `--evidence-file`, and `--rto-target-seconds`, reject missing, empty and flag-like values with an option-specific error. Reject unknown flags. Validate source and target database names as PostgreSQL identifiers acceptable to the runner (letters/underscores first, then letters/digits/underscores; bounded to PostgreSQL's 63-byte identifier limit), and reject equality. Retain the protected targets `postgres`, `template0`, `template1`, `acres`; also reject any source/target combination that could cause the source to be dropped. Validate the RTO as a positive integer in a safe arithmetic range before using it or writing evidence. Validate credentials before connection; do not print passwords or environment dumps. Do not make a merely reachable `pg_isready` server count as a completed restore.
2. **Never destroy a pre-existing target database.** After readiness and authenticated source/maintenance access, check whether the requested drill database already exists. If it does, fail with a clear non-destructive error before dump creation or restore, including when `--keep-drill-db` is present. Create the target only after the backup archive passes `pg_restore --list`. Perform target creation as an individually checked operation; set the cleanup ownership flag only after confirmed creation. Use `ON_ERROR_STOP=1` for all operational SQL. Remove the unconditional pre-create `DROP DATABASE IF EXISTS`. Use a safe maintenance connection for target existence, creation and cleanup, and make source inspection failures fail closed. Never terminate sessions or drop a target that this invocation did not create. The optional `--keep-drill-db` remains explicit and documented.
3. **Treat backup and cleanup as owned resources.** Give each run a unique private dump path under `--backup-dir` (including concurrent same-second runs) and restrictive permissions from creation. Do not overwrite an existing path or follow a predictable symlink. Track only the archive created by this invocation. Preserve existing `--keep-backup` semantics. On normal exit and all failures/signals after target creation, attempt cleanup of the owned target and archive; report cleanup failure and return nonzero rather than printing a successful outcome. Publish success evidence only after required cleanup succeeds (or an explicit keep flag skips that cleanup), so a cleanup failure cannot leave an approvable success report. Make the cleanup path idempotent and prevent cleanup errors from masking the original failure. If safe target cleanup cannot be confirmed, retain the archive/evidence needed for investigation and report the target name. Document the behavior for interruption and permission failure.
4. **Make verification and evidence truthful.** `_prisma_migrations` source/restored query failures must abort rather than become zero. Validate count query outputs as nonnegative integers before arithmetic or JSON emission, require source/restored table and migration equality, PostGIS presence, zero unvalidated FKs and record-count parity. Measure RTO using millisecond elapsed time against `RTO_TARGET_SECONDS * 1000` so a fractional-second overrun cannot pass by integer truncation. An RTO miss must exit nonzero and must never write a success report. Preserve the fields and strict basic UTC `drill_timestamp` required by `validateRestoreReport`: `status: "success"`, `rto_compliant: true`, positive `backup_bytes`, nonnegative finite `duration_ms`, equal safe integer table/migration counts, and true parity/PostGIS/FK flags only after verification. Serialize paths and values safely as JSON (including spaces/quotes in an evidence path); write evidence atomically so an interrupted writer cannot leave a partial success artifact. A failed run may write an explicit `status: "failed"` report, but it must not be acceptable to Category 6. Preserve the Stage 7 output path and existing accepted success field names.
5. **Add `scripts/ops/run-restore-drill.spec.js`.** Use Node's built-in `node:test`/`assert` and a temporary PATH containing small, isolated `pg_isready`, `psql`, `pg_dump`, and `pg_restore` stubs; the real `restore-postgres.sh` must use only those stubbed commands in the test. No test may contact the real PostgreSQL service, use production credentials, or create/drop a real database. Record stub calls and assert order and target names. Test help, unknown/missing/flag-like options, invalid names and RTO, equal/protected databases, missing password, unavailable Postgres, pre-existing target rejection with zero DROP and zero dump calls, successful creation/restore/verification and Category 6 JSON shape, custom paths containing spaces, retention flags, RTO boundary and overrun, malformed/mismatched query data, dump/list/restore failures, and cleanup after an owned target is created. Assert that no success evidence is emitted on failures and that a cleanup failure returns nonzero. Use a fresh temporary directory and remove it after each case.
6. **Wire the gate and record the result.** Add `ops:restore-drill-test` to root `package.json` and include it in `ops:check`. Add the test file to `scripts/ops/check-production-templates.sh`'s required files; add focused static assertions only for invariants the test harness cannot exercise reliably. Update `docs/operations.md` and `docs/launch-checklist.md` with the committed behavior, test evidence and residual live-drill requirements. Do not mark Category 6 or Phase 12 complete, alter the readiness example to approved, or invent an operator sign-off.

## Expected impact and non-goals

- The changed entry point is the operations CLI and its root npm gate; there are no HTTP routes or UI changes. Stage 7 keeps calling the same runner and consuming its successful child evidence. A pre-existing target, invalid input, failed check, RTO miss or failed cleanup produces a nonzero exit and cannot be used as an approved restore report.
- This work does not run against live PostgreSQL or Garage, change backup schedules, assess off-host encryption/freshness, reconcile storage objects, or supply production RPO/RTO evidence. Category 6 still needs an operator-authorized live restore and separate Garage reconciliation report; `docs/launch-checklist.md` specifies that authorization and sign-off boundary.
- Rollback is a revert of this implementation commit. If a live invocation leaves an owned drill database after cleanup failure, the operator investigates it under the documented runbook rather than having an automated retry drop an arbitrary database.
