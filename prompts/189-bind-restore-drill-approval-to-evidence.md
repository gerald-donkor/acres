# 189 — bind restore drill approval to its evidence

## Scope and why this is next

The committed baseline is `68060b1bd2456730f7ffcd2a5c9d2f9c5f9980f7` on `main`, with a clean worktree at planning time. Prompt 188 made the Category 6 UTC backup start cadence consistent with the declared recovery point objective (RPO). The next dependency-safe gap is the restore claim: an approved `backup_and_disaster_recovery` section currently accepts `restore_drill_completed: true`, any nonempty `restore_drill_date` string, and narrative `evidence`, even when no successful restore drill artifact is referenced. Generic evidence parsing rejects known failure flags if a JSON file happens to be listed, but does not require a restore artifact or bind its run date to the operator's claim.

Require one explicit, successful, machine-readable restore drill artifact for Category 6 approval and make `restore_drill_date` match its UTC run date. Keep the separate PostgreSQL/Garage reconciliation and backup-coverage requirements visible: this change proves only consistency of a referenced restore report with the approval record, not the authenticity of the report or achieved production RPO.

## Implementation contract

1. Add a focused helper in `scripts/ops/check-launch-readiness.js` that validates a restore child report as a complete successful report. Recognize it by validated report structure, not a filename alone. Require the exact success flags above (`status`, RTO, parity, PostGIS, foreign keys), finite nonnegative integral source/restored table and migration counts with equality, positive integral `backup_bytes`, finite nonnegative duration, and a valid UTC `drill_timestamp`. Reject missing, null, wrong-type, contradictory, future-dated, impossible-calendar, or failed fields. Use a deterministic `now` supplied through the validator's existing options for date tests, defaulting to the real current time for CLI use. Do not copy untrusted report values into blocker messages.
2. Parse `drill_timestamp` strictly as `YYYYMMDDTHHMMSSZ` and round-trip its UTC components so invalid dates cannot normalize silently. Require `restore_drill_date` on approved Category 6 to be an actual UTC calendar date in `YYYY-MM-DD`, or the ISO UTC timestamp form already used by the fixture; normalize both to the UTC date for comparison. Reject free text, timezone offsets and future dates. Do not impose an arbitrary maximum age: that requires a separately approved operator policy. If more than one valid restore report is referenced, select the latest `drill_timestamp` deterministically and require the declared date to match that report. A malformed or failed referenced restore report remains a blocker even when another succeeds; do not let wildcard matching choose only the convenient result.

Treat absent/unreadable/invalid report, invalid date, and date disagreement as bounded Category 6 blockers. Avoid echoing file contents, database names, paths containing credentials, or supplied dates in new diagnostics.
