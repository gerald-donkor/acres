## Behavior, failure, rollout, and rollback

- The exporter is an unauthenticated metrics endpoint reachable only from private Compose peers. A compromised peer can read operational metadata or cause repeated scrape load. Limit its database permissions, collection time, exposed listener, and label detail. No public route, tenant identifier, SQL text, DSN, or password may appear in Prometheus output or dashboard JSON.
- An exporter process can be up while database access fails. Panels and runbooks must show both `up{job="acres-postgres"}` and the exporter’s database-scrape success signal; a failed DB collection must never be presented as a healthy zero connection count. Avoid an automatic role reconciliation at every application startup or on every scrape.
- Sequence promotion: create/inject monitor secret file; reconcile/verify role on existing database using the controlled operator path; deploy exporter; verify private HTTP scrape and metric semantics; reload/promote Prometheus and Grafana; observe `up` plus exporter success. Keep application traffic working if optional observability is unavailable. For a fresh database, the bootstrap path creates the role before exporter starts.
- Rollback removes exporter service, secret mount/reference, scrape, and new panels, leaving the monitor role harmless but present unless the operator separately revokes it after verifying no other consumer. Do not roll back app schema, app roles, or the existing API/worker metrics. Document the telemetry blind spot during rollback.
- No static visual delta or 375/800/1280 breakpoint behavior exists for this operator-only infrastructure change.
