# 188 — validate backup cadence against the recovery point objective

## Scope and why this is next

The committed baseline is `2416e77d4b2e301a6fb009f8b90b1d89fdfd3280` on `main`; the worktree was clean when this prompt was prepared. Prompt 187 is implemented and committed. Phase 12K now has structured child evidence for all seven launch-drill stages, but the Phase 12 exit still requires operator-owned live infrastructure and approval. The next dependency-safe repository gap is Category 6 backup scheduling: `infra/launch/readiness.example.json` states `rpo_hours: 1` and `backup_schedule_cron: "0 2 * * *"` (one run per day in the scheduler's timezone). `scripts/ops/check-launch-readiness.js` only checks that the cron value is a string. An operator could therefore approve a daily backup schedule under a one-hour RPO without a blocker. The approved test fixture repeats that contradiction.

Make the schedule field a narrow, auditable UTC cadence contract. An approved Category 6 record must use a supported every-hour cron form whose longest interval between scheduled starts is no greater than its declared RPO. Change the example to an hourly schedule. This is a static lower-bound check, not proof of completed backups, replication to an encrypted off-host destination, a Garage backup, or restore success. Those remain operator evidence and the existing live drill gate. The image-provenance and protected-promotion steps still need an operator-approved registry, attestation policy, and environment; this step does not select them.

## Implementation contract

1. In `scripts/ops/check-launch-readiness.js`, add a small pure, exported function for validating the supported `backup_schedule_cron` grammar and computing its maximum cyclic gap in scheduled start times. Keep it close to the Category 6 gate or in a small sibling module if that makes testing clearer. Use the repository's existing CommonJS/Node patterns; no new runtime dependency or shell invocation is needed.
2. Supported syntax is exactly five ASCII whitespace-separated cron fields. Require hour, day-of-month, month, and day-of-week to each be `*`; the minute field may be `*`, a single decimal integer `0..59`, `*/n` with positive decimal integer `1..60`, or a comma-separated list of distinct decimal integers `0..59`. Reject empty list members, duplicate minute values, leading signs, out-of-range values, nondecimal text, macros (`@daily`), seconds/six-field forms, ranges, named months/days, and any restricted hour/day/month/weekday expression. Do not accept unsupported syntax by guessing its runtime semantics. Explicitly document the supported subset and that scheduling must use UTC on the operator host. If implementation finds a valid common form that can be supported without ambiguity, add it only with equivalent gap tests and docs.
3. Expand the minute field into distinct sorted minute values. Compute the largest interval between adjacent occurrences, including the wrap from the last minute in one hour to the first minute in the next hour. The all-minute expression has a one-minute maximum gap. Return structured data such as `{ valid, maxGapMinutes, reason }` without echoing untrusted cron input. Reject a syntactically valid expression when `maxGapMinutes > rpo_hours * 60`; allow equality. Compare in minutes without rounding the RPO upward. A single minute such as `0 * * * *` has a 60-minute gap; `0,30 * * * *` has a 30-minute gap. A `*/n` expression is evaluated from actual expanded minutes, not assumed to have gap `n` at the hour boundary.
4. In the approved Category 6 branch, retain the existing numeric RPO/RTO checks and add one bounded blocker for a missing/unsupported schedule and one for a supported schedule whose maximum gap exceeds the RPO. Guard invalid `rpo_hours` so cadence comparison does not yield a misleading secondary result. Do not echo a supplied expression or environment value in blocker text. Preserve existing behavior for unresolved template sections and all other categories.
5. Change `infra/launch/readiness.example.json` to `"backup_schedule_cron": "0 * * * *"`, consistent with the example's one-hour RPO. Update the approved fixture in `scripts/ops/check-launch-readiness.spec.js` to the same cadence; ensure existing valid-record tests continue to represent a coherent approved record. In `scripts/ops/check-production-templates.sh`, statically assert the example's backup cron and RPO are coherent using the same validator or a narrow contract check that cannot silently drift from it. Avoid a circular invocation of the whole template check.
6. Add behavior-focused tests in the existing readiness spec: hourly exactly meets a one-hour RPO; every 30 minutes meets a half-hour RPO; all-minute syntax; nonuniform minute lists and the wrap-around interval; `*/n` values that do and do not meet a fractional RPO; a daily expression blocked under a one-hour RPO; a single hourly run blocked under a half-hour RPO; unsupported/six-field/malformed inputs; duplicates/out-of-range values; and one case showing a bad schedule cannot approve Category 6 even when the other Category 6 fields and evidence strings are present. Verify unrelated categories still behave as before. Tests must be deterministic and require no live PostgreSQL, Garage, cron daemon, or credentials.
7. Update `docs/operations.md`, `docs/launch-checklist.md` Category 6, and the Phase 12 verification record in `docs/build-plan.md` with the actual validation behavior, supported syntax, example change, test results, and remaining operator-owned requirements. Explicitly state that scheduled start frequency alone cannot establish the RPO: operators must show successful completion, off-host encrypted transfer, PostgreSQL and Garage coverage, freshness, and a restore drill under actual load. Do not mark formal launch approval complete.

## Expected impact, limits, and rollback

- No application route, schema, API, UI, asset, production job, or CI permission changes. Only launch-readiness approval decisions, the checked-in example/fixture, and operations documentation change.
- A previously accepted approved readiness record with a daily, unsupported, or too-slow schedule will fail closed. The operator updates it to a real UTC schedule whose proven maximum start gap fits the selected RPO, or supplies an approved future extension to the parser. Do not silently reinterpret a local-time cron schedule as UTC.
- This prompt does not install a scheduler, create a backup destination, encrypt a dump, publish an OCI image, select a registry or secret store, attest provenance, run a live restore, or approve the launch. Actual backup success and freshness need independent evidence; a passing cron check must never be described as recovery compliance.
- Rollback is reverting the new cron validation and example in one change if the supported subset proves incompatible with the operator's chosen scheduler; do not weaken the RPO numeric gate or substitute a fictional schedule.
