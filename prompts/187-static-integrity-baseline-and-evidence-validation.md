# 187 — static integrity baseline and evidence validation

## Scope and why this is next

The committed baseline is `1f9afcd` on `main`; the worktree was clean when this prompt was prepared. This is the next dependency-safe Phase 12K step under `docs/build-plan.md` §13 and `docs/launch-checklist.md` §§2–4, 7. Prompts 182–186 added structured baselines and launch-readiness cross-validation for stages 2–7 of the seven-stage Unified Launch Evidence Dossier. Stage 1 (`static_templates`) still executes `check-production-templates.sh`, `check-docker-runtime.sh`, and `scan-secrets.sh` as one shell chain, then records only `summary.staticIntegrity: "passed" | "failed"`. It has no structured child artifact and no check-by-check evidence. A dossier consumer therefore cannot verify which of these three checks ran, nor distinguish a failed check from one skipped by `&&` short-circuiting.

Create one bounded static-integrity runner that executes the existing three checks, always writes structured evidence (including on failure), and returns nonzero unless all three pass. Feed it into stage 1, aggregate a `staticIntegrityBaseline` and `summary.staticIntegrityCompliance` from the child artifact, and validate both child and dossier evidence at launch readiness. Keep the existing `summary.staticIntegrity` field for compatibility. This is repository/static evidence, not operator sign-off or a claim that a live release is ready.

## Implementation contract

1. Add `scripts/ops/run-static-integrity-checks.js` as a Node CLI and testable module. The production CLI must invoke the exact fixed command set, in this order, from the repository root: `bash scripts/ops/check-production-templates.sh`, `bash scripts/ops/check-docker-runtime.sh`, `bash scripts/ops/scan-secrets.sh`. Use `spawnSync`/`execFileSync` with an argument array, not a shell-interpolated command. Continue to the next check after a failure so the artifact reports all three; catch spawn errors and record a failed check. Do not let a user-supplied command or path override the production check set. Export a small pure result-building function or dependency-injected runner for deterministic unit tests.
2. Support `--output <file>` and `-o <file>`; reject a missing value and unknown flags with nonzero exit. An output file is required when stage 1 invokes the runner. Resolve it relative to the current working directory, create its parent directory, write atomically via a same-directory temporary file plus rename, and return nonzero if writing fails. Preserve no raw stdout/stderr or matched secret text in JSON. The runner may print fixed check labels and generic pass/fail status to stage logs, but never scanner output, credentials, environment values, or command error messages that could contain matched text.
3. Evidence schema (`static-integrity-evidence-<timestamp>.json`): `drill_type: "static_integrity_verification"`, ISO `timestamp`, `status: "success" | "failed"`, `valid: boolean`, `totalChecks: 3`, `passedChecks: 0..3`, `failedChecks: 0..3`, and `checks` as exactly three objects ordered by stable IDs `production_templates`, `docker_runtime`, `secret_defaults`. Each check has `passed: boolean` and a numeric `exitCode` when a process exited; a spawn failure may use `exitCode: null` with a generic fixed `failureKind: "spawn_failed"`. The artifact records no unbounded or secret-bearing output. `status === "success"` and `valid === true` only when all three checks exit zero; the CLI exit code must match that verdict.
4. Replace stage 1's chain in `scripts/ops/run-launch-drills.sh` with `node scripts/ops/run-static-integrity-checks.js --output "${EVIDENCE_DIR}/static-integrity-evidence-${STAMP}.json"`. Let `run_stage` discover the child artifact. In dossier aggregation, find the stage 1 child artifact from its listed artifacts and parse it defensively. Mark `staticIntegrityBaseline.status: "verified"` only when stage 1 is `PASSED`, the child has the expected `drill_type`, success/valid verdict, exact three distinct expected check IDs, all `passed === true` with `exitCode === 0`, and consistent `totalChecks`, `passedChecks`, and `failedChecks`. Include the three check summaries and counts in the verified baseline. Otherwise set `status: "breached"` with a generic error message. Set `summary.staticIntegrityCompliance` to `"passed"` or `"failed"` from that verdict. Preserve `summary.staticIntegrity` for existing readers. Missing, malformed, stale, or contradictory child evidence fails closed; never infer success from stage exit status alone.
5. In `scripts/ops/check-launch-readiness.js` `checkEvidenceFile`, recognize stage 1 child evidence by `drill_type` or the `static-integrity-evidence-` filename. Reject malformed/missing check arrays, omitted or duplicate IDs, inconsistent counts, nonzero or missing successful exit codes, `valid !== true`, or `status !== "success"`. Also reject dossiers with `staticIntegrityBaseline.status !== "verified"` when that field is present, and `summary.staticIntegrityCompliance !== "passed"` when that field is present. Keep preexisting dossier and older evidence behavior compatible; do not require the new fields on unrelated historical evidence files. Use bounded, generic blocker text that identifies the failed check ID, never contents of scanner output.
6. Extend `scripts/ops/check-production-templates.sh` to require the new runner and spec file and to assert that the launch orchestrator wires the stage 1 artifact, baseline, and compliance flag. Avoid introducing a circular invocation: the template check verifies the runner file and integration text, but does not execute the runner.
7. Add `scripts/ops/run-static-integrity-checks.spec.js` with meaningful cases for all-pass, each individual check failing while later checks still run, spawn failure, CLI missing/unknown arguments, artifact write failure, exact schema/counts, and absence of captured secret text. Use isolated fake commands or injected execution in unit tests; do not modify production files or put secret-looking literals in scanned source. Extend `run-launch-drills.spec.js` to assert a real stage 1 child artifact in the artifact list, its three passing checks in the offline drill, the verified baseline, and the compliance flag. Extend `check-launch-readiness.spec.js` with explicit child/dossier breach cases and a passing case. Include mismatched count, duplicate/missing check ID, and false-success cases. No test should need live Postgres, Garage, Docker daemon, or operator credentials.
8. Update `docs/operations.md`, `docs/launch-checklist.md` (stage 1 artifact/schema and checklist use), and the relevant Phase 12 verification record in `docs/build-plan.md` with measured results and the remaining operator-owned launch blockers. Do not claim formal launch approval.
